


# 电商「事件驱动订单处理系统」架构设计

适用于：

* 高并发下单
* 秒杀
* 分布式库存
* 最终一致性
* 微服务
* 多仓库
* 异步履约
* 高可用
* 可观测性

# 一、核心目标

Amazon 级订单系统的核心目标：

| 目标    | 说明          |
| ----- | ----------- |
| 高可用   | 单服务故障不影响整体  |
| 高吞吐   | 百万级订单/分钟    |
| 最终一致性 | 不做全局分布式事务   |
| 解耦    | 服务之间通过事件通信  |
| 可扩展   | 任意扩容        |
| 可重试   | 消息丢失/失败自动恢复 |
| 幂等    | 防止重复扣库存     |
| 可观测   | 全链路追踪       |

# 三、核心思想：事件驱动（EDA）

传统：

```text
下单
 -> 调库存
 -> 调支付
 -> 调物流
```

问题：

* 强耦合
* 同步阻塞
* 一个服务失败全链路失败
* RT 高
* 难扩容

Amazon 风格：

```text
OrderCreatedEvent
```

谁需要谁消费：

* Inventory Service
* Payment Service
* Risk Service
* Coupon Service
* Recommendation Service
* Notification Service

彻底解耦。

# 四、订单状态机（非常重要）

订单系统本质：

# = 状态机

```text

  ↓
PENDING_PAYMENT
  ↓

  ↓

  ↓
```

```text

```

建议：

# 所有状态变更必须事件化

例如：

```text

OrderCancelledEvent
```

# 六、为什么 Amazon 不做分布式事务？

因为：

# 两阶段提交（2PC）在超大规模会崩

问题：

| 问题    | 说明     |
| ----- | ------ |
| 锁资源   | 性能差    |
| 协调者单点 | 风险高    |
| 网络分区  | 易阻塞    |
| 扩展性差  | 不适合互联网 |

因此：

# Amazon 使用 Saga + 最终一致性

---

# 七、Saga 模式（核心）

订单流程：

```text
创建订单
 -> 扣库存
 -> 支付
 -> 发货
```

失败怎么办？

使用：

# 补偿事务

例如：

```text
库存扣减失败
 -> 取消订单

支付失败
 -> 回滚库存

发货失败
 -> 退款
```

---

# Choreography（事件编排）

# 十、Outbox Pattern（生产核心）

避免：

```text
数据库成功
Kafka失败
```

方案：

# Outbox Pattern

Order Service：

```text
事务：
  1. 写 orders
  2. 写 outbox_events
COMMIT
```

CDC：

* Debezium
* Maxwell
* Canal

监听 binlog：

```text
outbox_events -> Kafka
```

保证：

# 数据和事件一致

# 十一、Kafka Topic 设计

推荐：

```text

payment-failed

```

不要：


否则：

* Topic 巨大
* 难治理
* Consumer 混乱

# 十二、分区设计（超关键）

订单：

```text

```

保证：

# 同一订单事件有序

否则：

```text

```

可能乱序。

# 十三、库存系统（最难）

Amazon 最核心难点：

# 库存一致性

---

# 库存冻结流程

```text
OrderCreated
    ↓
ReserveInventory
    ↓
InventoryReserved
```

不是直接扣减：

```text
available_stock --
```

而是：

```text
reserved_stock ++
```

支付成功：

```text
reserved --
sold --
```

支付失败：

```text
reserved --
```

---

# 十四、防超卖方案

核心：

# 原子库存扣减

SQL：

```sql
UPDATE inventory
SET reserved = reserved + 1
WHERE sku = ?
AND available - reserved > 0
```

返回：

```text
affected_rows == 1
```

成功。

# 二十、事件溯源（Event Sourcing）

高级玩法：

订单不存最终状态。

只存：

```text

OrderPaid

```

当前状态：

```text

```

优点：

* 完整审计
* 时间旅行
* 可回溯

缺点：

* 实现复杂
* 学习成本高

Amazon 部分系统会用。

# 二十九、生产级关键经验（非常重要）

---

# 1. 不要同步调用太多服务

错误：

```text
Order
 -> Inventory
 -> Coupon
 -> Payment
 -> Logistics
```

RT 会爆炸。

---

# 2. 不要追求强一致

互联网：

# 最终一致 > 强一致

---

# 3. Kafka 不保证业务幂等

必须：

业务层自己做。

---

# 4. 消息一定会重复

必须接受。

---

# 5. 重试会导致雪崩

必须：

* 指数退避
* Dead Letter Queue
* Retry Topic

---
