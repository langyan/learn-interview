
# 各层连接的最大值与配置分析

这几层是串联关系,瓶颈取决于最小的那一层,而不是最大的那一层。

## 1. Tomcat 连接(NIO Connector)

| 参数 | 默认值 | 含义 |
|---|---|---|
| `maxThreads` | 200 | 同时处理请求的工作线程数 |
| `maxConnections` | 8192 (NIO) | Tomcat 同时接受和维持的 TCP 连接总数 |
| `acceptCount` | 100 | 连接数达到 maxConnections 后,操作系统层面的等待队列(backlog) |
| `minSpareThreads` | 10 | 最小空闲线程 |
| `connectionTimeout` | 20000ms | 建立连接后等待请求数据的超时 |
| `keepAliveTimeout` / `maxKeepAliveRequests` | 同 connectionTimeout / 100 | 长连接保持时间与单连接最大请求数 |

Spring Boot 对应配置:

```yaml
server:
  tomcat:
    threads:
      max: 200
      min-spare: 10
    max-connections: 8192
    accept-count: 100
    connection-timeout: 20s
```

**实际并发上限:** 同时处理的请求数是 maxThreads,能保持的连接数是 maxConnections,再往后最多排队 acceptCount,超出后连接被拒绝。
**系统层限制:** `ulimit -n`(文件描述符)、`net.core.somaxconn`、`tcp_max_syn_backlog` 会限制上面的值,需要同步调大。

## 2. 数据库连接池(应用侧)

| 连接池 | 最大连接数参数 | 默认值 | 其他关键参数 |
|---|---|---|---|
| **HikariCP** | `maximumPoolSize` | 10 | `minimumIdle`(默认等于最大值)、`connectionTimeout` 30s、`idleTimeout` 10min、`maxLifetime` 30min、`leakDetectionThreshold` 默认关闭 |
| **Druid** | `maxActive` | 8 | `initialSize` 0、`minIdle` 0、`maxWait` -1(无限等待,建议设置) |
| **DBCP2** | `maxTotal` | 8 | `maxIdle` 8、`minIdle` 0、`maxWaitMillis` -1 |
| **Tomcat JDBC** | `maxActive` | 100 | `maxWait` 30s |

**大小估算:** 常用经验公式是 `连接数 ≈ CPU核数 × 2 + 有效磁盘数`(指数据库服务器)。单实例通常 10~50 就够用,并不是越大越好。连接池应当明显小于 Tomcat 的 maxThreads,因为并非所有请求都访问数据库。
**注意:** Druid 和 DBCP 的 maxWait 默认无限等待,连接池耗尽时线程会一直挂起,最终拖垮 Tomcat 线程池。生产环境要显式设置。
**Hikari 建议:** `maxLifetime` 要比数据库或中间件(如防火墙、负载均衡)的空闲断开时间短几十秒。

## 3. Redis 连接

**服务端:**

| 参数 | 默认值 | 说明 |
|---|---|---|
| `maxclients` | 10000 | 实际上限还受 `ulimit -n` 限制(需要预留约 32 个描述符) |
| `timeout` | 0 | 客户端空闲断开时间,0 表示不断开 |
| `tcp-keepalive` | 300 | 心跳检测 |
| `tcp-backlog` | 511 | 需同步调整 `somaxconn` |

云 Redis(阿里云、腾讯云等)通常按规格限制最大连接数,以实例规格为准。

**客户端:**

| 客户端 | 默认行为 |
|---|---|
| **Lettuce** | 默认所有线程共享一个连接(基于 Netty,线程安全),普通命令不需要连接池。池化只用于事务、阻塞命令等场景,需引入 `commons-pool2`,默认 `max-active=8`、`max-idle=8`、`min-idle=0`、`max-wait=-1` |
| **Jedis** | 必须用连接池,`maxTotal=8`、`maxIdle=8`、`minIdle=0`、`maxWait=-1` |
| **Redisson** | `connectionPoolSize=64`、`connectionMinimumIdleSize=24`、`subscriptionConnectionPoolSize=50` |

**要点:** Redis 命令是单线程执行的,连接数越多不会提升吞吐,反而增加开销。连接总量要满足:`实例数 × 单实例最大连接数 < maxclients`,并为运维、监控等留余量。Jedis 默认的 8 个连接在高并发下很容易成为瓶颈,同时要设置 `maxWait`。

## 4. 数据库服务端连接

| 数据库 | 参数 | 默认值 | 备注 |
|---|---|---|---|
| **MySQL** | `max_connections` | 151 | 可调到几千,但每个连接占内存;`wait_timeout` 默认 28800 秒 |
| **PostgreSQL** | `max_connections` | 100 | 每个连接是一个独立进程(约 5~10MB),连接数大时建议使用 PgBouncer |
| **Oracle** | `processes` / `sessions` | 视版本而定 | `sessions ≈ processes × 1.5 + 22` |
| **SQL Server** | 最大用户连接 | 32767 | 受内存限制 |

查看命令(MySQL):

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Max_used_connections';  -- 历史峰值
SHOW STATUS LIKE 'Threads_connected';     -- 当前连接
SHOW PROCESSLIST;
```

## 5. 容量核算(最重要)

```
数据库:  Σ(应用实例数 × 连接池 max) + 定时任务/运维/其他系统 ≤ max_connections × 80%
Redis:   Σ(应用实例数 × 客户端连接数) + 其他 ≤ maxclients × 80%
应用:    Tomcat maxThreads ≥ 数据库连接池 max(多数请求不是都访问数据库)
```

示例:部署 4 个实例,每个 Hikari max=20,共 80 个连接,加上运维和任务约 20 个,在 MySQL 默认的 151 内是安全的。但 K8s 扩容到 10 个副本后就是 200,会超限。**弹性伸缩时必须重新核算。**

## 6. 常见故障特征

- **Tomcat 线程耗尽:** 响应变慢,接口超时,线程 dump 中大量线程停在等待连接池获取连接上
- **连接池耗尽:** `Connection is not available, request timed out after 30000ms`(Hikari),通常由慢 SQL、事务未关闭、连接泄漏引起
- **MySQL `Too many connections`:** 总连接数超过 max_connections
- **Redis `ERR max number of clients reached`:** 超过 maxclients,多为连接泄漏或实例过多
- **Redis `Could not get a resource from the pool`(Jedis):** 池耗尽

# 补充:Nginx 层与 Linux 层,以及全链路汇总

## 一、Nginx 层

### 1. 连接数上限

| 参数 | 默认值 | 含义 |
|---|---|---|
| `worker_processes` | 1(建议 `auto`) | worker 进程数,通常等于 CPU 核数 |
| `worker_connections` | 512(很多发行版配置文件写 1024) | **单个 worker** 能同时打开的连接数上限,包含客户端连接和上游连接 |
| `worker_rlimit_nofile` | 系统默认 | worker 的文件描述符上限,需要 ≥ `worker_connections` |
| `listen ... backlog` | Linux 下 511 | 监听队列长度,实际受 `somaxconn` 限制 |

**最大并发的计算:**

```
最大客户端连接 = worker_processes × worker_connections
反向代理场景:每个请求占 2 个连接(客户端→Nginx、Nginx→上游)
最大并发请求 ≈ worker_processes × worker_connections / 2
```

例如 4 核、`worker_connections 10240`,理论连接数 4 万,代理并发约 2 万。如果上游没有开 keepalive,还会产生大量短连接,受端口和 TIME_WAIT 限制(见 Linux 层)。

### 2. 超时与长连接

| 参数 | 默认值 | 说明 |
|---|---|---|
| `keepalive_timeout` | 75s | 客户端长连接空闲时间 |
| `keepalive_requests` | 1000(1.19.10 之前是 100) | 单个长连接最大请求数 |
| `client_header_timeout` / `client_body_timeout` | 60s | 读取请求头/请求体超时 |
| `proxy_connect_timeout` | 60s | 连接上游超时(建议 3~5s) |
| `proxy_read_timeout` / `proxy_send_timeout` | 60s | 读写上游超时,按业务最长接口调整 |
| `client_max_body_size` | 1m | 请求体上限,上传接口必须调大 |
| `send_timeout` | 60s | 向客户端发送响应的超时 |

### 3. 上游(Nginx→Tomcat)连接配置

默认 Nginx 到上游用 HTTP/1.0 短连接,**每个请求新建一次 TCP 连接**,高并发下极易耗尽端口。必须开启上游长连接:

```nginx
upstream tomcat_pool {
    server 10.0.0.11:8080 max_conns=2000 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:8080 max_conns=2000 max_fails=3 fail_timeout=10s;
    keepalive 256;              # 每个 worker 保留的空闲长连接数
    keepalive_requests 10000;
    keepalive_timeout 60s;      # 必须小于 Tomcat 的 keepAliveTimeout
}

server {
    location / {
        proxy_pass http://tomcat_pool;
        proxy_http_version 1.1;
        proxy_set_header Connection "";   # 清除 close,否则长连接不生效
        proxy_connect_timeout 3s;
        proxy_read_timeout 60s;
    }
}
```

要点:
- `keepalive` 只是**空闲**长连接缓存的数量,不限制总连接数。真正限制单个上游并发的是 `max_conns`。
- `max_conns` 应小于等于 Tomcat 的 `maxConnections`(且总和要考虑 Nginx 实例数)。
- Nginx 的上游 `keepalive_timeout` 要**小于** Tomcat 的 `keepAliveTimeout`,否则 Tomcat 先关闭连接,Nginx 复用时会出现 502 或 `upstream prematurely closed connection`。
- 开源版 Nginx 的 `queue`(上游排队)是商业版功能,开源版超过 `max_conns` 会直接返回 502/503。

### 4. 限流

```nginx
limit_conn_zone $binary_remote_addr zone=perip:10m;
limit_req_zone  $binary_remote_addr zone=reqs:10m rate=50r/s;
limit_conn perip 100;
limit_req  zone=reqs burst=100 nodelay;
```

限流是保护后端的第一道防线,Nginx 拒绝的成本远低于让请求打到 Tomcat 再失败。

### 5. 常见报错

| 现象 | 原因 |
|---|---|
| `worker_connections are not enough` | worker_connections 不足 |
| `socket() failed (24: Too many open files)` | 文件描述符不足,检查 `worker_rlimit_nofile` 和 systemd 的 `LimitNOFILE` |
| `connect() failed (99: Cannot assign requested address)` | 到上游的本地端口耗尽,未开 keepalive 或端口范围太小 |
| `upstream timed out (110)` / 504 | 上游处理慢,超过 `proxy_read_timeout` |
| `upstream prematurely closed connection` / 502 | 上游主动断开,常是 keepalive 超时不匹配或 Tomcat 重启 |
| `no live upstreams` | 所有上游被 `max_fails` 标记为不可用 |

## 二、Linux 层

Linux 层是所有上层配置的"天花板"。上层参数调得再大,系统限制不放开也不生效。

### 1. 文件描述符(每个连接占用一个 fd)

| 参数 | 默认值 | 说明 |
|---|---|---|
| `ulimit -n`(nofile) | 1024(软限制) | 单进程可打开的 fd 数。Nginx、Tomcat、Redis 都受此约束 |
| `fs.file-max` | 随内存计算,通常几十万以上 | 系统级总 fd 上限 |
| `fs.nr_open` | 1048576 | 单进程 fd 的硬上限,`ulimit -n` 不能超过它 |

关键点:**通过 systemd 启动的服务不读 `/etc/security/limits.conf`**,需要在 service 文件里设置:

```ini
[Service]
LimitNOFILE=655350
```

容器和 K8s 中的 fd 上限继承自容器运行时(containerd/docker)的默认值,也需要检查。

### 2. TCP 队列与端口

| 参数 | 默认值 | 说明 |
|---|---|---|
| `net.core.somaxconn` | 128(内核 5.4 起为 4096) | accept 队列上限,`listen(backlog)` 取两者最小值。Nginx 的 511、Tomcat 的 acceptCount、Redis 的 tcp-backlog 都受它限制 |
| `net.ipv4.tcp_max_syn_backlog` | 128~1024,随内存变化 | 半连接(SYN)队列 |
| `net.core.netdev_max_backlog` | 1000 | 网卡收包队列,高流量时调大 |
| `net.ipv4.ip_local_port_range` | 32768 60999(约 2.8 万个) | 本机主动发起连接可用的端口范围 |
| `net.ipv4.tcp_syncookies` | 1 | 防 SYN 洪水 |

**端口限制是最容易被忽略的瓶颈:** 一个"源 IP + 目标 IP + 目标端口"组合,本机最多同时拥有约 2.8 万个连接。Nginx→单个 Tomcat、应用→单个 Redis、应用→单个数据库,都受此约束。再加上 TIME_WAIT 要保持 60 秒,不使用长连接时每秒新建连接数超过约 470 就会耗尽端口(28000 ÷ 60)。

### 3. TIME_WAIT 与保活

| 参数 | 默认值 | 说明 |
|---|---|---|
| `net.ipv4.tcp_tw_reuse` | 2(仅回环) | 设为 1 允许出向连接复用 TIME_WAIT 端口,适合 Nginx 作为客户端的场景 |
| `net.ipv4.tcp_max_tw_buckets` | 随内存变化 | TIME_WAIT 数量上限,超出直接丢弃 |
| `net.ipv4.tcp_fin_timeout` | 60 | 只影响 FIN_WAIT_2,**不能缩短 TIME_WAIT**(TIME_WAIT 固定 60 秒) |
| `net.ipv4.tcp_keepalive_time` / `intvl` / `probes` | 7200 / 75 / 9 | 死连接检测,默认要两个多小时才开始探测 |

注意:不要开启 `tcp_tw_recycle`,它在 4.12 内核已被删除,在 NAT 环境下会造成连接失败。

### 4. conntrack(防火墙/NAT/K8s 场景)

| 参数 | 说明 |
|---|---|
| `net.netfilter.nf_conntrack_max` | 连接跟踪表上限,默认按内存计算(常见 65536~262144) |
| `net.netfilter.nf_conntrack_tcp_timeout_established` | 默认 432000(5 天) |

开启 iptables、firewalld、kube-proxy 或 NAT 时,每个连接都占一条记录。表满后的现象是 `nf_conntrack: table full, dropping packet`,表现为随机超时、丢包,应用侧看不到明显错误。K8s 节点上特别容易出现。

### 5. 线程与内存

| 参数 | 默认值 | 说明 |
|---|---|---|
| `kernel.pid_max` | 32768(新版 systemd 系统可达 4194304) | 进程 + 线程总数上限,Java 线程也占用 |
| `kernel.threads-max` | 随内存计算 | 系统线程总数 |
| `ulimit -u`(nproc) | 随发行版 | 单用户进程/线程数 |
| `vm.max_map_count` | 65530 | 单进程内存映射数,线程多的 JVM 可能触及 |
| `net.ipv4.tcp_rmem` / `tcp_wmem` | 4096 131072 6291456 | 单连接收发缓冲区,连接数大时关注总内存 |

每个 Java 线程默认栈 1MB(`-Xss`),Tomcat 200 线程约占 200MB 栈空间,不在堆内,计算容器内存时要计入。

### 6. 推荐配置示例

```bash
# /etc/sysctl.d/99-tuning.conf
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 8192
net.core.netdev_max_backlog = 16384
net.ipv4.ip_local_port_range = 10240 65000
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_keepalive_time = 600
net.ipv4.tcp_keepalive_intvl = 30
net.ipv4.tcp_keepalive_probes = 5
net.netfilter.nf_conntrack_max = 1048576
fs.file-max = 2097152
```

### 7. 排查命令

```bash
ulimit -n; cat /proc/<pid>/limits | grep "open files"   # 进程 fd 上限
ls /proc/<pid>/fd | wc -l                                # 进程当前 fd 数
ss -s                                                    # 连接状态汇总
ss -ant | awk 'NR>1{s[$1]++}END{for(k in s)print k,s[k]}'  # 各状态数量
ss -lnt                                                  # Recv-Q/Send-Q:监听队列当前/上限
netstat -s | grep -i -E "overflow|drop"                  # 队列溢出统计
sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max
dmesg | grep -i conntrack
```

`ss -lnt` 中监听端口的 Recv-Q 持续接近 Send-Q,说明 accept 队列将满,应用处理不过来或队列配置过小。

## 三、全链路汇总

```
客户端
  ↓ ① Linux: fd、somaxconn、syn_backlog
Nginx:  worker_processes × worker_connections
  ↓ ② Linux: 端口范围、TIME_WAIT、conntrack(Nginx→上游)
Tomcat: maxConnections / maxThreads / acceptCount
  ↓ 
  ├→ 数据库连接池 (Hikari max) ──→ 数据库 max_connections
  └→ Redis 客户端连接 ──────────→ Redis maxclients
        (每个出向连接同样受 fd、端口范围、conntrack 限制)
```

| 层级 | 关键上限 | 典型默认值 | 生产参考 |
|---|---|---|---|
| Linux fd | `ulimit -n` | 1024 | 65535 以上 |
| Linux 队列 | `somaxconn` | 128 / 4096 | 4096~65535 |
| Nginx | `worker_connections` | 512 | 10240~65535 |
| Tomcat 连接 | `maxConnections` | 8192 | 按实例规格,通常 8192~20000 |
| Tomcat 线程 | `maxThreads` | 200 | 200~800,看业务是否 IO 密集 |
| DB 连接池 | `maximumPoolSize` | 10 | 20~50 |
| Redis 客户端 | Lettuce 共享连接 / Jedis 8 | | Jedis 建议 50~200 |
| Redis 服务端 | `maxclients` | 10000 | 一般够用 |
| 数据库 | `max_connections` | 151 / 100 | 按总连接核算 |

**配置原则(从外到内逐层收敛):**

1. **每一层的上限要小于等于下一层能承受的量,并且有序收敛。** 外层放大、内层卡死,会导致请求在中间层排队、超时。
2. **超时要逐层递减。** 例如 Nginx `proxy_read_timeout` > 应用接口超时 > 数据库/Redis 超时,避免上层已经放弃、下层还在空耗资源。
3. **长连接超时要外短内长。** 上游空闲超时(Nginx 到 Tomcat)要比 Tomcat 的 keepAliveTimeout 短,防止复用已被对端关闭的连接。
4. **扩容前重新核算。** 副本数增加会让数据库和 Redis 的总连接数线性增长,Nginx 实例数增加会让 Tomcat 的连接数增长。

# 全链路连接上限与配置总表,以及日活 1 万的配置方案

下面的数值基于我设定的流量假设(第一节),不是你系统的实测值。如果你的接口数、响应时间不同,请按第七节调整,并以压测结果为准。

## 一、容量模型(DAU 10,000)

| 项 | 假设/计算 | 结果 |
|---|---|---|
| 日请求量 | 人均 100 次接口请求 × 1 万 | 约 100 万/天 |
| 平均 QPS | 100 万 ÷ 86400 | 约 12 |
| 峰值 QPS | 80% 流量集中在约 4.8 小时,再乘 2 倍瞬时波动 | 约 100 |
| **设计 QPS** | 峰值再留 3 倍余量 | **约 300** |
| 峰值同时在线 | DAU 的 10%~15% | 1,000~1,500 人 |
| 并发处理中请求 | 并发 = QPS × 响应时间(Little 定律),300 × 0.2s;慢接口按 0.5s 算 | 60(慢时约 150) |
| 数据库并发 | 300 QPS × 60% 访问 DB × 30ms DB 耗时 ≈ 5.4,再乘 4 倍(慢 SQL、事务) | 约 20 |
| Redis 吞吐 | 300 QPS × 约 5 条命令 | 约 1,500 ops/s(单实例能力 5 万以上) |
| 出口带宽 | 100 QPS × 50KB ≈ 40Mbps,设计值约 100Mbps | 静态资源走 CDN |

**结论:1 万 DAU 属于中小规模,默认值附近的配置已基本够用。真正要做的是让各层参数互相匹配、做好超时和保护,而不是把数字调大。**

## 二、推荐部署规格

| 组件 | 规格 | 数量 | 说明 |
|---|---|---|---|
| Nginx | 2C4G | 2 | keepalived 主备,或使用云 SLB |
| 应用(Tomcat) | 4C8G | 2 | 最低 HA 要求;K8s 下 2 副本起步 |
| MySQL | 4C16G + SSD | 1 主 1 从 | 若查询重可用 8C16G |
| Redis | 2~4GB | 1 主 1 从 + 哨兵 | 或云 Redis 主备版 |

## 三、全链路参数总表

| 层 | 参数 | 默认值 | 10k DAU 推荐 | 说明 |

## 四、各层配置示例

### 1. Linux(所有节点)

```bash
# /etc/sysctl.d/99-tuning.conf
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 4096
net.ipv4.ip_local_port_range = 10240 65000
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_keepalive_time = 600
net.ipv4.tcp_keepalive_intvl = 30
net.ipv4.tcp_keepalive_probes = 5
fs.file-max = 1048576
net.netfilter.nf_conntrack_max = 262144
```

```ini
# systemd service(Nginx / Tomcat / Redis)
[Service]
LimitNOFILE=65535
```

数据库和 Redis 主机另外设置 `vm.swappiness=1`。Redis 主机还需设置 `vm.overcommit_memory=1` 并关闭透明大页(THP)。

### 2. Nginx

```nginx
worker_processes auto;
worker_rlimit_nofile 65535;
events { worker_connections 10240; use epoll; }

http {
    keepalive_timeout 65;
    keepalive_requests 1000;
    client_max_body_size 20m;

    # 按 IP 限流;办公网等 NAT 出口会共用 IP,阈值要留足
    limit_req_zone  $binary_remote_addr zone=reqs:10m rate=50r/s;
    limit_conn_zone $binary_remote_addr zone=perip:10m;

    upstream app {
        least_conn;
        server 10.0.0.11:8080 max_conns=1000 max_fails=3 fail_timeout=10s;
        server 10.0.0.12:8080 max_conns=1000 max_fails=3 fail_timeout=10s;
        keepalive 64;
        keepalive_requests 10000;
        keepalive_timeout 60s;       # 必须小于 Tomcat keepAliveTimeout(75s)
    }

    server {
        location / {
            limit_req  zone=reqs burst=100 nodelay;
            limit_conn perip 50;
            proxy_pass http://app;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_connect_timeout 3s;
            proxy_read_timeout 60s;
            proxy_send_timeout 60s;
        }
    }
}
```

### 3. Tomcat + JVM

```yaml
server:
  tomcat:
    threads: { max: 200, min-spare: 20 }
    max-connections: 8192
    accept-count: 100
    connection-timeout: 10s
    keep-alive-timeout: 75s
    max-keep-alive-requests: 10000
```

```
-Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200
-XX:MaxMetaspaceSize=512m -XX:+HeapDumpOnOutOfMemoryError
```

8G 内存的分配:堆 4G,Metaspace 约 0.5G,线程栈约 0.2G(200 线程 × 1MB),直接内存和其他约 0.5~1G,其余留给操作系统。

### 4. 数据库连接池(Hikari)

```yaml
spring:
  datasource:
    url: jdbc:mysql://db:3306/app?connectTimeout=3000&socketTimeout=30000
    hikari:
      maximum-pool-size: 20
      minimum-idle: 10
      connection-timeout: 3000
      idle-timeout: 600000
      max-lifetime: 1500000      # 25 分钟,小于 wait_timeout
      leak-detection-threshold: 30000   # 上线初期或排查时开启
```

另外要给 SQL 设置语句级超时(如 MyBatis `defaultStatementTimeout=10`),否则一条慢 SQL 会长期占住连接。

## 五、链路核算

| 检查项 | 计算 | 结论 |
|---|---|---|
| 请求并发 vs Tomcat 能力 | 设计峰值处理中请求 60~150;Tomcat 2 × 200 线程,Nginx 每台 1000 | 通过,有余量 |
| 数据库总连接 | 2 × 20 = 40,加运维、监控、复制、定时任务约 30,合计约 70,占 500 的 14% | 通过 |
| 扩容余量 | 按 80% 利用率,400 ÷ 20 ≈ 20 个副本才触顶 | 通过 |
| 线程池 vs 连接池 | 线程 400,DB 连接 40,约 10:1;超过时线程最多等 3s 就失败 | 合理,但慢 SQL 会触发排队 |
| Redis 连接数 | Lettuce 共享连接,总计个位数到几十 | 远低于 maxclients |
| Nginx fd | 客户端 2~8 千 + 上游约 128,远小于 65535 | 通过 |
| 端口/TIME_WAIT | Nginx→Tomcat 走长连接,基本没有新建连接压力 | 通过 |
| 超时链 | Nginx 读 60s > 应用接口 30s > SQL 10s > Redis 2s;Hikari 3s | 逐层递减 |
| 长连接超时 | Nginx 上游 60s < Tomcat 75s | 避免复用已关闭连接导致 502 |

## 六、监控指标与扩容触发条件

| 层 | 监控项 | 告警/扩容阈值 |
|---|---|---|
| Nginx | `stub_status`、`ss -lnt` 的 Recv-Q、502/504 比例 | Recv-Q 持续接近 Send-Q;5xx 超过 0.1% |
| Tomcat | 繁忙线程数、`tomcat_threads_busy` | 使用率持续超过 70% |
| Hikari | `hikaricp_connections_active`、`pending`、`timeout` 次数 | pending 持续大于 0 |
| MySQL | `Threads_running`、`Max_used_connections`、慢查询 | Threads_running 超过核数 × 2;已用连接超过 max 的 60% |
| Redis | `connected_clients`、`used_memory`、`evicted_keys`、慢日志 | 内存超过 75%;出现 evicted |
| Linux | `nf_conntrack_count`、`netstat -s` 的 overflow、fd 使用量 | conntrack 超过 80%;overflow 持续增长 |
| JVM | GC 暂停、老年代占用 | Full GC 频繁;老年代长期高于 70% |

上线前至少做一次压测(JMeter、k6 或 wrk),目标是 300 QPS 稳定运行 30 分钟以上,并观察上表指标。

## 七、假设变化时怎么调整

| 场景 | 峰值 QPS | 调整方向 |
|---|---|---|
| 本文基准(人均 100 请求/天) | 约 100(设计 300) | 本文配置 |
| 重度或实时类(人均 500 请求/天,大屏轮询) | 约 500 | 应用 3~4 实例,连接池总量约 80,接口加缓存 |
| 含 WebSocket/长轮询 | 取决于在线人数 | 长连接占用 maxConnections 和 fd,按在线人数规划,不能按 QPS 估算 |
| 活动突发(峰值 × 5~10) | 500~1000 | 提前扩容,Nginx 限流,热点数据缓存,写操作异步化 |
| 增长到 10 万 DAU | 约 1000 | 应用 4~6 实例,连接池总量约 100(DB 并发 72 = 1000 × 60% × 30ms × 4),读写分离,Redis 升级规格或集群 |

最容易变化的两个假设是人均请求数和 DB 耗时。如果你能提供人均日请求数、核心接口平均响应时间、数据库类型,以及是否有 WebSocket 或文件上传,我可以重新核算一遍。需要的话,也可以把这份整理成一份 Word 或在线文档,方便留存和分享。
