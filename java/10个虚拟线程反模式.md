# 修复了这10个虚拟线程反模式后，我们的Java应用变得更快

> 我们发现了10个虚拟线程的反模式。修复后，我们的Java应用速度大大提升


---

我认识的一位开发者曾半开玩笑地说："Java 21给了我们虚拟线程。为什么我们还像2015年那样配置线程池？"

这是个容易产生的想法。你会读到Project Loom，看到基准测试显示数百万个虚拟线程，突然间那些精心调校的`ThreadPoolExecutor`配置看起来像是遗迹。所以你把它们拔出来。你切换到 `Executors.newVirtualThreadPerTaskExecutor()`。你部署。

然后，三天后，你的数据库就被烧毁了。

这不是假设。这是我见过的模式——坦白说，我也不得不调试。问题不在于虚拟线程不好。它们在合适的工作负载下确实具有变革性。问题在于，它们消除了一个特定的瓶颈——昂贵的平台线程——而系统中其他所有限制完全未被触及。

- 你的数据库仍然有连接池限制。
- 你的CPU核心依然有限。
- 你的下游API仍然有速率限制。
- 你的锁仍然串行访问。
- 你的内存依然有限。

**虚拟线程让并发变得便宜。它们不会让你的系统无限。**

以下是十个我会在将生产 Spring Boot 服务迁移到虚拟线程前提醒另一位工程师注意的反模式。这些都不是理论上的担忧。这些错误在代码审查中看起来合理，却在凌晨4点引发事故。

## 为什么虚拟线程会改变并发（但不会改变容量）

在深入反模式之前，先建立心理模型。

**平台线程很贵。** 每个线程映射到操作系统线程，消耗大约1MB的栈内存，并需要内核级调度。这就是为什么我们花了几十年时间构建线程池——创建线程成本高，所以我们会重复使用线程。池大小实际上成为并发限制。

**虚拟线程会颠倒这个。** 它们是由JVM管理的，不是操作系统。它们制造成本低——你可以拥有数百万。当一个虚拟线程在I/O上阻塞时，JVM会将其从载体线程中卸载，从而释放该载体以运行其他虚拟线程。结果是：你可以实现巨大的并发，而不会按比例消耗资源。

这对于I/O密集型负载来说确实非常强大。等待数据库调用的REST API不需要专用操作系统线程。它需要一种高效暂停和恢复的方法。虚拟线程正是提供了这些。

但关键区别在于：**虚拟线程解决的是线程瓶颈，而不是资源瓶颈。**

如果你的数据库能处理100个并发连接，那么让1万个虚拟线程等待这些连接也帮不上忙。这只是意味着有9,900个线程被排队，消耗内存并可能超时。**并发增加；但容量没有。**

这就是所有反模式的核心张力。

## 反模式1：将虚拟线程视为通用线程池的替代品

第一个错误是最广泛的：在没有重新考虑每个执行器实际操作的情况下，将应用中的每个执行服务替换为 `Executors.newVirtualThreadPerTaskExecutor()`。

这看起来很吸引人，因为它简化了配置。不再有调优池大小的问题。不再纠结是用 `newCachedThreadPool()` 还是 `newFixedThreadPool(50)` 了。直接用虚拟线程，让JVM自己去处理。

问题在于并非所有并发都相同。以下几者之间有区别：

- **并发**：同时进行多个任务
- **CPU并行性**：实际上同时执行多个任务
- **资源限制**：下游系统的有限容量

虚拟线程在并发方面表现出色。它们不创建CPU核心。它们不会扩展数据库连接池。它们不会增加网络带宽。

考虑一个执行大量计算的批处理作业：

```java
// Problematic: virtual threads for CPU-bound work
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var item : largeDataset) {
        executor.submit(() -> performCpuIntensiveAnalysis(item));
    }
}
```

乍一看，这似乎没问题。但如果 `performCpuIntensiveAnalysis` 真的是CPU密集型——比如图像处理或密码学操作——你实际上是在制造成千上万个虚拟线程，争夺同样的八个CPU核心。JVM的fork-join池会处理调度，但你没有获得任何收益。你增加了开销。

对于CPU受限工作，更好的方法是使用一个与可用核心规模相匹配的有界池：

```java
// Better: bounded parallelism for CPU-bound work
int cores = Runtime.getRuntime().availableProcessors();
try (var executor = Executors.newFixedThreadPool(cores)) {
    for (var item : largeDataset) {
        executor.submit(() -> performCpuIntensiveAnalysis(item));
    }
}
```

这并不是说虚拟线程在这里有问题——它们不会破坏任何东西。但它们也帮不上忙。工作负载受限于CPU，线程的巧妙设计也改变不了这一点。

> **虚拟线程可能仍然可接受时**：如果你的"CPU受限"任务偶尔在I/O上阻塞，或者计算时间足够短，调度开销占主导，虚拟线程是可以的。关键是要了解你的实际工作量，而不是假设。

## 反模式2：虚拟线程池化

旧习难改。我见过这样的代码：

```java
// Anti-pattern: pooling virtual threads
ExecutorService virtualThreadPool = Executors.newFixedThreadPool(
    1000,
    Thread.ofVirtual().factory()
);
```

这个意图是可以理解的。我们被训练成会池化线程，因为线程成本高。创建虚拟线程池感觉是负责任的做法。

但这忽略了虚拟线程的全部意义。它们制造和摧毁成本低。池化它们就像池化 `ArrayList` 实例——你解决了一个已经不存在的问题。

正确的模式是为每个任务创建一个新的虚拟线程：

```java
// Correct: one virtual thread per task
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var request : requests) {
        executor.submit(() -> handleRequest(request));
    }
}
```

每个任务都有自己的虚拟线程。任务完成后，线程被丢弃。JVM对此处理效率很高。

这里有个细微差别。虽然将虚拟线程本身池化没什么意义，但**限制并发任务数量**仍然有价值。如果你调用一个有速率限制的外部 API，你需要绑定并发性：

```java
// Bounding concurrent tasks, not pooling threads
var semaphore = new Semaphore(50); // Max 50 concurrent calls

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var request : requests) {
        executor.submit(() -> {
            semaphore.acquire();
            try {
                return callExternalApi(request);
            } finally {
                semaphore.release();
            }
        });
    }
}
```

区别很重要：你是在限制对有限资源的访问，而不是重用线程。虚拟线程让这种模式更简洁，因为你不必调整池的大小——你只需控制对瓶颈的访问。

> **虚拟线程池化何时可能可接受**：基本上永远不可接受。如果你发现自己正在创建虚拟线程池，你可能误解了这个模型。应使用信号量或类似机制来限制并发。

## 反模式3：因为"虚拟线程很便宜"而忽略背压

这是生产环境中最危险的地方。

场景是这样的：

```
HTTP requests (20,000 concurrent)
        ↓
Virtual threads (20,000)
        ↓
Database calls (20,000)
        ↓
Database connection pool (100 connections)
        ↓
Requests waiting for connections
        ↓
Latency increases
        ↓
Timeouts
        ↓
Retries
        ↓
Even more load
```

虚拟线程让接受巨大并发变得轻而易举。一个使用虚拟线程每请求的Spring Boot应用可以处理数万个同时请求而不会线程耗尽。这感觉像是一场胜利。

但你的数据库连接池仍然只有100个连接。你的Redis连接池仍然只有50个。你的外部API仍然有每秒1,000个请求的速率限制。

当20,000个请求都试图获取数据库连接时会发生什么？

它们排队。它们等待。延迟攀升。最终，请求超时。客户端重试。重试增加了更多负载。系统螺旋式上升。

这是一个具体的问题示例：

```java
// Anti-pattern: unbounded concurrency without backpressure
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    // Each request runs on its own virtual thread
    // 20,000 concurrent requests = 20,000 virtual threads
    // All competing for 100 database connections
    return userRepository.findById(id).orElseThrow();
}
```

虚拟线程没问题。数据库不是。

修复方法是引入**背压**——一种当下游资源饱和时限制有多少请求进入系统的机制。这可以采取多种形式：

```java
// Better: bounded concurrency with backpressure
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    if (!databaseSemaphore.tryAcquire()) {
        throw new ServiceUnavailableException("System at capacity");
    }
    try {
        return userRepository.findById(id).orElseThrow();
    } finally {
        databaseSemaphore.release();
    }
}
```

或者，更优雅地，配置你的连接池使用合理的超时，让池本身提供背压：

```yaml
# application.yml
spring:
  datasource:
    hikari:
      maximum-pool-size: 100
      connection-timeout: 5000  # Fail fast instead of queuing forever
```

关键是虚拟线程**不会**消除对背压的需求。如果说有什么影响，它们让背压更加重要，因为它们允许如此多的并发到达你的瓶颈。

> **这个反模式何时可接受**：如果你的下游系统确实能处理无限并发（罕见），或者你在更高层（API网关、负载均衡器）有明确的速率限制，你可能不需要应用级背压。但要验证这个假设。

## 反模式4：在持有锁时执行阻塞操作

这个需要一些细微差别，因为行为在不同Java版本中已经改变。

经典建议是：不要在阻塞时持有锁，因为在Java 21中，虚拟线程在持有监视器时阻塞会**钉住（pin）**其载体线程。钉住意味着载体线程无法被其他虚拟线程重用，违背了虚拟线程的目的。

这是有问题的模式：

```java
// Problematic in Java 21: blocking while holding a synchronized lock
public synchronized User fetchUser(Long id) {
    // This database call blocks
    // In Java 21, this pins the carrier thread
    return userRepository.findById(id).orElseThrow();
}
```

在Java 21（JEP 444）中，这是一个真正的问题。`synchronized` 关键字使用基于监视器的锁定，当虚拟线程在 `synchronized` 块内阻塞时，JVM无法卸载它。载体线程被钉住。

然而，这在JEP 491中已经改变，该JEP在Java 24中交付。**从Java 24开始，虚拟线程在 `synchronized` 块内阻塞时不再钉住载体线程。** JVM现在可以正确卸载它们。

这是一个重要的区别。如果你在Java 21上，建议是：避免在阻塞操作期间持有 `synchronized` 锁。改用 `ReentrantLock`，它一直支持虚拟线程卸载：

```java
// Better for Java 21: use ReentrantLock for blocking operations
private final ReentrantLock lock = new ReentrantLock();

public User fetchUser(Long id) {
    lock.lock();
    try {
        return userRepository.findById(id).orElseThrow();
    } finally {
        lock.unlock();
    }
}
```

如果你在Java 24或更高版本上，这个担忧基本已经解决。但 `ReentrantLock` 通常仍然更可取，原因还有其他：它支持超时、可中断的锁获取和公平排队。

> **synchronized何时可接受**：在Java 24+中，`synchronized` 块不再钉住虚拟线程。即使在Java 21中，如果 `synchronized` 块不包含阻塞操作，也没有问题。问题特指在持有锁时阻塞。

## 反模式5：在数百万虚拟线程下粗心使用ThreadLocal

`ThreadLocal` 几十年来一直是Java开发的中流砥柱。像Spring这样的框架用它来存储请求上下文、安全主体和事务状态。它也是虚拟线程的一个潜在内存问题——不是因为 `ThreadLocal` 本身不好，而是因为数学变了。

在200个平台线程的池中，每个变量最多有200个实例。使用虚拟线程，你可能有100,000个并发线程，每个都有自己的 `ThreadLocal` 状态。

```java
// Potentially problematic with high virtual thread counts
private static final ThreadLocal<RequestContext> CONTEXT = 
    ThreadLocal.withInitial(RequestContext::new);
```

如果 `RequestContext` 是一个小对象，内存影响可能可控。但如果它持有对大型对象的引用——解析的请求体、缓存数据等——堆压力会迅速累积。

还有生命周期问题。虚拟线程是短命的。如果你不清理 `ThreadLocal` 值，它们可能残留，导致陈旧状态或内存泄漏：

```java
// Better: explicit cleanup
private static final ThreadLocal<RequestContext> CONTEXT = new ThreadLocal<>();

public void handleRequest(Request request) {
    try {
        CONTEXT.set(new RequestContext(request));
        processRequest();
    } finally {
        CONTEXT.remove();  // Important with virtual threads
    }
}
```

对于沿调用栈向下传递的不可变上下文数据，**Scoped Values**（Java 25中最终确定，早期版本中为预览）提供了更清晰的模型：

```java
// Scoped Values: cleaner for immutable context
private static final ScopedValue<RequestContext> CONTEXT = 
    ScopedValue.newInstance();

public void handleRequest(Request request) {
    ScopedValue.where(CONTEXT, new RequestContext(request))
        .run(() -> processRequest());
}
```

Scoped Values是不可变的，在作用域结束时自动清理，并且是为虚拟线程设计的。它们不是所有用例的直接替代品，但对于请求上下文传播，它们是更好的选择。

> **ThreadLocal何时可接受**：`ThreadLocal` 不会消失。许多库依赖它。关键是理解内存影响并确保正确清理。如果你的每线程状态很小并且你正确清理，`ThreadLocal` 仍然可行。

## 反模式6：期望虚拟线程为CPU密集型工作带来性能奇迹

这与反模式#1有重叠，但值得单独讨论，因为误解太常见了。

虚拟线程是为**I/O密集型**工作负载设计的——大部分时间在等待的任务。当一个虚拟线程在数据库调用、HTTP请求或文件读取上阻塞时，JVM可以卸载它并将载体线程用于其他事情。效率提升就来自这里。

**CPU密集型工作不同。** 如果你的任务在执行大量计算，就没有阻塞可以卸载。CPU已经饱和。添加更多线程不会创造更多CPU。

```java
// Anti-pattern: virtual threads for pure CPU work
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var image : images) {
        executor.submit(() -> processImage(image));  // CPU-intensive
    }
}
```

`processImage` 方法可能花费100ms的纯计算。在虚拟线程上运行10,000个这样的任务不会让它们更快。这只是意味着10,000个虚拟线程在争夺相同的CPU核心，由JVM的调度器进行调解。

对比：

| I/O密集型工作负载 | CPU密集型工作负载 |
|---|---|
| CPU等待网络/磁盘/数据库 | CPU已经忙于计算 |
| 虚拟线程可以重叠等待 | 更多线程不会创造更多CPU |
| 吞吐量提高 | 吞吐量不变 |

对于CPU密集型工作，正确的方法是**有界并行**——通常大小设置为可用核心数：

```java
// Better: bounded parallelism for CPU-bound work
int parallelism = Runtime.getRuntime().availableProcessors();
try (var executor = Executors.newFixedThreadPool(parallelism)) {
    for (var image : images) {
        executor.submit(() -> processImage(image));
    }
}
```

> **虚拟线程何时可能仍然有效**：如果你的"CPU密集型"任务有间歇性阻塞——比如，计算50ms然后等待缓存查找——虚拟线程仍然可以提供好处。关键是分析你的实际工作负载，而不是假设。

## 反模式7：因为"数百万虚拟线程是可能的"而创建无限并发工作

围绕虚拟线程的营销强调规模："数百万个线程。"这在技术上是真的。JVM可以处理数百万个虚拟线程。但这并不意味着你应该创建它们。

考虑这个模式：

```java
// Anti-pattern: one virtual thread per item in a huge dataset
List<Order> orders = orderRepository.findAll();  // 500,000 orders
for (Order order : orders) {
    Thread.startVirtualThread(() -> processOrder(order));
}
```

乍一看，这看起来高效。虚拟线程很便宜，对吧？为什么不并发处理所有订单？

实际发生的情况是：

1. 创建500,000个虚拟线程
2. 每个都试图获取数据库连接（池大小：100）
3. 499,900个线程排队，消耗内存
4. 队列增长速度快于排空速度
5. 内存压力增加
6. GC更频繁地运行
7. 每个订单的延迟增加
8. 最终，OutOfMemoryError或超时级联

线程单独来看很便宜。500,000个线程，每个都持有一个 `Order` 对象的引用并等待连接池，并不便宜。

更好的方法是显式限制并发：

```java
// Better: bounded concurrency with a semaphore
var semaphore = new Semaphore(100);  // Match database pool size
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Order order : orders) {
        executor.submit(() -> {
            semaphore.acquire();
            try {
                processOrder(order);
            } finally {
                semaphore.release();
            }
        });
    }
}
```

或者使用带背压的反应式方法：

```java
// Alternative: reactive stream with backpressure
Flux.fromIterable(orders)
    .flatMap(order -> Mono.fromCallable(() -> processOrder(order))
        .subscribeOn(Schedulers.fromExecutor(
            Executors.newVirtualThreadPerTaskExecutor())),
        100)  // Concurrency limit
    .blockLast();
```

原则很简单：**便宜的线程并不意味着无限的工作。** 你的下游系统——数据库、API、消息队列——有有限的容量。有界并发尊重这些限制。

> **无限并发何时可能可接受**：如果每个任务完全自包含，没有共享资源——纯计算，没有I/O、没有锁、没有共享状态——那么创建许多虚拟线程问题较小。但这在生产系统中很罕见。

## 反模式8：用"发射后忘记"的虚拟线程替代结构化并发

虚拟线程使生成并发任务变得容易：

```java
// Anti-pattern: fire-and-forget concurrency
public DashboardData getDashboard(Long userId) {
    Thread.startVirtualThread(() -> fetchUserProfile(userId));
    Thread.startVirtualThread(() -> fetchRecentOrders(userId));
    Thread.startVirtualThread(() -> fetchRecommendations(userId));
    
    // How do we collect results? How do we handle failures?
    return assembleDashboard();  // This won't work correctly
}
```

这个模式看起来很吸引人，因为它简单。生成一些线程，让它们做自己的工作。但它会造成严重问题：

- **失败传播**：如果一个任务失败，你怎么知道？你如何取消其他任务？
- **结果收集**：任务异步运行。你什么时候组装结果？
- **生命周期管理**：如果请求被取消会发生什么？线程会继续运行吗？
- **异常处理**：虚拟线程中未捕获的异常会被记录，但除此之外被忽略。

**结构化并发**（Java 21–24中为预览，Java 25中作为JEP 505最终确定）通过将相关的并发任务视为一个单元来解决这个问题：

```java
// Better: structured concurrency
public DashboardData getDashboard(Long userId) throws Exception {
    try (var scope = StructuredTaskScope.open()) {
        var profileTask = scope.fork(() -> fetchUserProfile(userId));
        var ordersTask = scope.fork(() -> fetchRecentOrders(userId));
        var recommendationsTask = scope.fork(() -> fetchRecommendations(userId));
        
        scope.join();  // Wait for all tasks
        
        return new DashboardData(
            profileTask.get(),
            ordersTask.get(),
            recommendationsTask.get()
        );
    }
    // If any task failed, the scope is cancelled and exception propagates
}
```

结构化并发提供：

- **保证清理**：如果作用域退出，所有分叉任务都会被取消
- **失败传播**：如果一个任务失败，其他任务可以被取消
- **结果汇总**：等待所有任务，然后收集结果
- **清晰生命周期**：任务被范围限定到一个区块

> **重要版本说明**：结构化并发在Java 21–24中为预览，最终在Java 25中完成。API已经发展壮大。如果你使用的是Java 21，你需要启用预览功能，并且要注意API可能与最终版本不同。

> **"发射后忘记"何时可接受**：对于真正独立的后台任务，且失败不会影响主流程——日志记录、指标、缓存预热——则发射后忘记是可以的。关键词是"独立"。

## 反模式9：在不了解阻塞库行为的情况下使用它们

虚拟线程改变了阻塞的运作方式。I/O上的虚拟线程阻塞没问题——它会从载体卸载，释放出其他工作空间。但这并不意味着每一次阻塞操作都自动安全或高效。

以JDBC为例：

```java
// This is fine with virtual threads
try (var connection = dataSource.getConnection()) {
    // Virtual thread blocks here, but it's fine
    // The carrier thread is released
    var result = connection.createStatement()
        .executeQuery("SELECT * FROM users WHERE id = " + id);
    // ...
}
```

这没问题。虚拟线程卸载，载体线程负责其他工作。但数据库连接池的容量仍然有限。如果有10,000个虚拟线程都试图从100个连接的池中获取连接，那么9,900个线程会等待。

这就是我之前提到的区别：

- "虚拟线程可以阻塞" ✓
- "基础资源是无限的" ✗

HTTP客户端也是如此：

```java
// Blocking HTTP call - fine for virtual threads
var response = httpClient.send(request, BodyHandlers.ofString());
```

如果你用的是 `java.net.http.HttpClient`，它支持虚拟线程。但如果你使用的是内部依赖线程池的老客户端，或者有自己的连接限制，你需要了解这些限制。

有些库内部使用 `synchronized` 方式可能导致钉住（Java 21）或序列化访问。有些库维护自己的线程池。有些接口的连接限制在API上并不明显。

**迁移到虚拟线程之前，先审查你的依赖：**

- 库会用 `synchronized` 来阻塞路径吗？（适用于Java 21）
- 它会维护内部线程池吗？
- 它有连接限制或速率限制吗？
- 它是为高并发设计的吗？

> **阻塞库何时没问题**：大多数设计良好的库都能很好地配合虚拟线程。关键是要理解它们的资源限制，而不是完全避免。

## 反模式10：迁移到虚拟线程却未测量真正的瓶颈

这就是涵盖所有其他模式的**元反模式**。

迁移过程看起来很简单：

```java
// Before
ExecutorService executor = Executors.newFixedThreadPool(200);

// After
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
```

只有一行代码变了。还能出什么问题呢？

**如果你不去衡量，那就是一切。**

虚拟线程并不会自动提升性能。它们改变了并发模型。这是否有效完全取决于你的瓶颈在哪里。

**迁移前，测量：**

- **吞吐量**：每秒请求，每秒任务
- **延迟**：p50、p95、p99 响应时间
- **CPU利用率**：你是CPU受限吗？
- **内存使用**：堆、GC频率、GC暂停时间
- **数据库池使用情况**：活跃连接数，等待时间
- **连接池饱和**：连接池总是满吗？
- **队列深度**：任务排队速度是否比耗尽速度快？
- **错误率**：超时、失败、重试
- **下游延迟**：依赖是否在变慢？

**迁移后，测量同样的量。比较一下。**

我见过迁移时，虚拟线程的吞吐量提升了10倍。我也见过迁移，数据库成了瓶颈，导致虚拟线程只是更多线程等待连接，导致迁移没有任何变化。

**迁移不是性能策略。这是并发模型的变革。性能影响取决于你的工作负载。**

```java
// A migration without measurement is a gamble
// This might help, or it might just move the queue
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
```

> **何时跳过测量**：绝不。即使你确信虚拟线程会有帮助，也要测量确认。生产系统总能让你感到惊喜。
