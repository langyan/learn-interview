### 1. HashMap JDK8 底层原理 & 线程不安全

**底层结构：** 数组 + 链表 + 红黑树

- 默认容量 16，负载因子 0.75
- 链表长度 ≥ 8 且数组长度 ≥ 64 时，链表转红黑树
- 扩容时容量翻倍，重新 rehash

**为什么线程不安全：**
- `put` 操作没有加锁，多线程并发写会导致**数据覆盖**
- 扩容时多线程操作可能导致**死循环**（JDK7 头插法，JDK8 尾插法改善但仍不安全）
- 推荐使用 `ConcurrentHashMap`（分段锁 / CAS + synchronized）

### 2. synchronized 锁升级 & ReentrantLock 选型

**锁升级过程（单向，不可降级）：**
```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
```
- **偏向锁：** 只有一个线程访问，Mark Word 记录线程ID
- **轻量级锁：** 多线程竞争但不激烈，CAS 自旋
- **重量级锁：** 竞争激烈，挂起线程，OS 级别互斥

**支付场景选型：**

| 场景 | 推荐 |
|------|------|
| 简单同步、代码块短 | synchronized |
| 需要超时、可中断、公平锁 | ReentrantLock |
| 支付扣款（需要超时防死锁） | **ReentrantLock** `tryLock(timeout)` |

### 3. JVM 内存结构 & FullGC 排查

**JVM 内存区域：**
- **堆（Heap）：** 对象存储，Young（Eden+S0+S1）+ Old
- **方法区/元空间：** 类信息、常量池
- **虚拟机栈：** 线程私有，栈帧
- **本地方法栈 / 程序计数器**

**线上频繁 FullGC 排查步骤：**
```bash
1. jstat -gcutil <pid> 1000   # 查看各区GC频率
2. jmap -heap <pid>            # 查看堆内存使用
3. jmap -histo <pid>           # 查看对象分布
4. 导出 dump: jmap -dump:format=b,file=heap.hprof <pid>
5. MAT/VisualVM 分析大对象、内存泄漏
```
**常见原因：** 大对象直接进老年代、内存泄漏、元空间不足、显式 `System.gc()`

### 4. InnoDB 为什么用 B+ 树 & 最左匹配失效

**为什么用 B+ 树：**
- 非叶节点只存 key，层高低（通常 3-4 层），**减少磁盘 IO**
- 叶节点双向链表，**范围查询高效**
- 相比 B 树，数据全在叶子，**扫表更稳定**

**最左匹配失效场景：**
```sql
-- 联合索引 (a, b, c)
SELECT * FROM t WHERE b = 1            -- ❌ 跳过a，失效
SELECT * FROM t WHERE a = 1 AND c = 1  -- ⚠️ 只用a，c失效
SELECT * FROM t WHERE a LIKE '%xxx'    -- ❌ 左模糊，失效
SELECT * FROM t WHERE a + 1 = 2       -- ❌ 函数/运算，失效
SELECT * FROM t WHERE a = 1 AND b > 1 AND c = 1 -- ⚠️ c失效（b范围后停止）
```

### 5. MySQL MVCC & undo log / read view

**MVCC 实现原理：**
- 每行数据有隐藏字段：`trx_id`（事务ID）、`roll_pointer`（回滚指针）
- 通过 undo log 形成**版本链**

**undo log 作用：**
- 记录数据修改前的值，用于**事务回滚**
- 为 MVCC 提供历史版本数据

**read view 作用：**
- 快照读时生成，记录当前活跃事务列表
- 判断某版本数据对当前事务**是否可见**
- RC（每次读生成新 read view） vs RR（事务首次读生成，不变）

### 6. Redis 缓存穿透、击穿、雪崩解决方案

| 问题 | 原因 | 级解决方案 |
|------|------|--------------|
| **穿透** | 查询不存在的key | ① 布隆过滤器拦截；② 空值缓存（TTL短） |
| **击穿** | 热点key过期，大量请求打DB | ① 互斥锁（只1个线程重建）；② 逻辑过期（不设TTL，异步更新） |
| **雪崩** | 大量key同时过期 | ① TTL加随机值；② 多级缓存；③ 熔断降级；④ Redis集群高可用 |

### 7. Redis 分布式锁缺陷 & 主从切换失效

**普通 SETNX 锁缺陷：**
- 主节点加锁成功，**未同步到从节点时主节点宕机**
- 从节点升为主节点，其他线程可再次加锁 → **锁失效**

**解决方案：**

```
方案1：Redlock（红锁）
- 向 N 个独立 Redis 节点加锁
- 超过半数（N/2+1）加锁成功才算成功
- 缺点：性能差、Martin Kleppmann 指出仍有缺陷

方案2：Zookeeper 分布式锁
- 基于临时顺序节点，天然解决主从问题

方案3：业务层幂等
- 依赖DB唯一约束/版本号做最终保障
```

### 8. Spring 事务传播机制 & @Transactional 失效场景

**7种传播机制：**

| 传播行为 | 说明 |
|---------|------|
| REQUIRED | 有事务加入，无则新建（默认） |
| REQUIRES_NEW | 总是新建，挂起原事务 |
| SUPPORTS | 有事务加入，无则非事务运行 |
| NOT_SUPPORTED | 非事务运行，挂起原事务 |
| MANDATORY | 必须在事务中，否则抛异常 |
| NEVER | 不能在事务中 |
| NESTED | 嵌套事务（保存点） |

**@Transactional 常见失效场景：**
```java
1. 同类内部调用（this.方法()）→ 绕过代理
2. 方法非 public
3. 异常被 catch 吞掉，未抛出
4. 抛出的是受检异常（默认只回滚 RuntimeException）
5. 数据库引擎不支持事务（如 MyISAM）
6. 多线程场景（事务绑定在 ThreadLocal）
```

### 9. 线程池 7 大参数 & 避免 OOM

**7大参数：**
```java
new ThreadPoolExecutor(
    corePoolSize,      // 核心线程数
    maximumPoolSize,   // 最大线程数
    keepAliveTime,     // 空闲线程存活时间
    TimeUnit.SECONDS,  // 时间单位
    workQueue,         // 任务队列
    threadFactory,     // 线程工厂
    handler            // 拒绝策略
);
```

**消息推送避免 OOM：**
- 使用**有界队列**（ArrayBlockingQueue），避免无界队列堆积
- 拒绝策略用 `CallerRunsPolicy`（调用方降速）或自定义（落库重试）
- 核心/最大线程数根据 IO 密集型计算：`线程数 = CPU核数 × (1 + 等待时间/计算时间)`
- 监控队列深度，动态调整参数（用动态线程池框架如 Hippo4j）

### 10. 手写 LRU 缓存（O(1) 读写）

```java
class LRUCache {
    private final int capacity;
    // 双向链表节点
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0); // 虚拟头
    private final Node tail = new Node(0, 0); // 虚拟尾

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        if (!map.containsKey(key)) return -1;
        Node node = map.get(key);
        moveToHead(node);  // 最近使用移到头部
        return node.val;
    }

    public void put(int key, int value) {
        if (map.containsKey(key)) {
            Node node = map.get(key);
            node.val = value;
            moveToHead(node);
        } else {
            Node node = new Node(key, value);
            map.put(key, node);
            addToHead(node);
            if (map.size() > capacity) {
                Node lru = removeTail(); // 淘汰最久未使用
                map.remove(lru.key);
            }
        }
    }

    // 核心：HashMap O(1)查找 + 双向链表 O(1)移动
    private void moveToHead(Node node) { removeNode(node); addToHead(node); }
    private void addToHead(Node node) {
        node.prev = head; node.next = head.next;
        head.next.prev = node; head.next = node;
    }
    private void removeNode(Node node) {
        node.prev.next = node.next; node.next.prev = node.prev;
    }
    private Node removeTail() {
        Node node = tail.prev; removeNode(node); return node;
    }

    class Node {
        int key, val;
        Node prev, next;
        Node(int k, int v) { key = k; val = v; }
    }
}
```
**淘汰逻辑：** 链表头 = 最近使用，链表尾 = 最久未使用，每次 get/put 将节点移到头部，容量满时删除尾节点。

### 1. Spring Bean 生命周期 & 三级缓存解决循环依赖

**完整生命周期：**
```
实例化（构造器）
    → 属性填充（依赖注入）
    → Aware 接口回调（BeanNameAware等）
    → BeanPostProcessor#postProcessBeforeInitialization
    → InitializingBean#afterPropertiesSet / init-method
    → BeanPostProcessor#postProcessAfterInitialization
    → 使用
    → DisposableBean#destroy / destroy-method
```

**三级缓存：**

| 缓存 | 存储内容 | 作用 |
|------|---------|------|
| 一级缓存 singletonObjects | 完整Bean | 正常使用 |
| 二级缓存 earlySingletonObjects | 半成品Bean（已实例化未注入） | 解决循环依赖 |
| 三级缓存 singletonFactories | ObjectFactory（Bean工厂） | 支持AOP代理 |

**为什么需要三级？** 若Bean需要AOP代理，二级缓存存的是原始对象，三级缓存通过工厂可以在循环引用时提前返回代理对象，保证注入的是代理。

### 2. 高并发下 DB 与缓存双写一致性

**常见方案对比：**

```
❌ 先写缓存再写DB：DB失败导致缓存脏数据
❌ 先写DB再更新缓存：并发下仍有不一致窗口

✅ Cache-Aside（推荐）：
   写：先写DB → 再删除缓存
   读：缓存miss → 读DB → 写缓存

✅ 延迟双删：
   删缓存 → 写DB → 延迟N毫秒 → 再删缓存
   （消除并发读在写DB期间重建的旧缓存）

✅ 实战方案：
   Canal 订阅 MySQL binlog → 异步删除/更新缓存
   + 消息队列保证删除重试
   + 缓存设置合理TTL兜底
```

### 6. 分布式事务 Seata AT/TCC/SAGA & 订单支付落地

**三种模式对比：**

| 模式 | 原理 | 性能 | 适用场景 |
|------|------|------|---------|
| **AT** | 自动补偿，框架生成undo log | 中 | 对业务无侵入，简单场景 |
| **TCC** | Try-Confirm-Cancel，业务自实现 | 高 | 高并发，强一致，支付核心链路 |
| **SAGA** | 长事务，补偿事务链 | 高 | 长流程，跨多服务，最终一致 |

**订单支付 TCC 落地：**
```
Try阶段：
  - 订单服务：冻结库存，订单状态→"待支付"
  - 账户服务：冻结金额

Confirm阶段：
  - 扣减库存，扣减金额，订单状态→"已支付"

Cancel阶段：
  - 释放冻结库存，释放冻结金额，订单→"已取消"

关键点：
  ✅ 幂等：每个阶段用 xid 去重
  ✅ 空回滚：Try未执行，Cancel需正常返回
  ✅ 悬挂：Cancel先于Try到达，Try需拒绝执行
```

## 1. 随机 UUID 列上放索引会发生什么？

随机 UUID 作为主键/索引时，B+Tree 插入位置高度随机，会导致：

- **页分裂和碎片化**：新值随机插入到已有页中间，页很快分裂。
- **缓存命中率低**：写入分散在整个索引，热页难以常驻内存。
- **写放大**：频繁磁盘 I/O、WAL/binlog 压力大。
- **范围查询不友好**：随机 UUID 没有时间局部性。

解决方式：

- 用 **顺序 ID**，如自增 BIGINT。
- 用 **时间排序 UUID**，如 UUIDv7、ULID、Snowflake。
- 如果必须用 UUIDv4，可考虑把随机部分后置，或使用数据库的聚簇索引策略调整。

核心：B+Tree 喜欢顺序插入，随机插入会破坏局部性。

## 2. 如何不用 OFFSET 分页 5000 万行？

用 **键集分页 / 游标分页**。

不推荐：

```sql
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 1000000;
```

数据库要扫描并丢弃前 100 万行。

推荐：

```sql
SELECT * FROM orders
WHERE id > :last_seen_id
ORDER BY id
LIMIT 20;
```

如果是复合排序：

```sql
WHERE (created_at, id) > (:last_created_at, :last_id)
ORDER BY created_at, id
LIMIT 20;
```

优点：

- 每次只从索引中定位到游标之后的位置。
- 查询时间与页深无关，基本稳定。
- 适合无限滚动、Feed、日志列表。

限制：

- 不能直接跳页。
- 排序字段必须有稳定唯一键，否则会漏行或重复。
- 需要把游标返回给客户端。

## 3. 什么时候用复合索引而不是两个独立索引？

当查询经常同时过滤、排序或连接多个列时，用复合索引。

例如：

```sql
SELECT * FROM orders
WHERE user_id = ?
ORDER BY created_at DESC;
```

更适合：

```sql
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);
```

而不是：

```sql
CREATE INDEX idx_orders_user ON orders(user_id);
CREATE INDEX idx_orders_created ON orders(created_at);
```

原因：

- 数据库通常一次扫描一个索引。
- 复合索引可以同时完成过滤和排序。
- `(A, B)` 索引可支持 `A`、`A+B` 查询，但通常不能单独高效支持 `B`。
- 列顺序很重要：等值过滤列在前，范围/排序列在后通常更好。

例外：

- 两列分别被大量独立查询使用。
- 索引过多影响写入，需要权衡。

## 4. 什么是 N+1 查询问题，如何解决？

N+1 指：

1. 先查 N 个用户：`SELECT * FROM users LIMIT 100;`
2. 然后循环每个用户，再查一次 profile：`SELECT * FROM profiles WHERE user_id = ?;`

结果：1 次主查询 + N 次子查询 = N+1。

解决：

- **显式 JOIN**：

```sql
SELECT u.*, p.*
FROM users u
LEFT JOIN profiles p ON p.user_id = u.id
WHERE u.id IN (...);
```

- **批量查询后内存组装**：

```sql
SELECT * FROM profiles WHERE user_id IN (...);
```

- **ORM 急加载**：如 JPA `JOIN FETCH`、Hibernate `@EntityGraph`、Rails `includes`、Django `select_related/prefetch_related`。
- 监控 ORM 生成的 SQL，避免懒加载在循环中触发。

## 5. 分布式系统中如何防止重复预订一张票？

核心：不要把“检查 + 预订”拆成两个无保护步骤。

方案：

### 悲观锁

```sql
BEGIN;
SELECT * FROM seats WHERE id = ? AND status = 'available' FOR UPDATE;
UPDATE seats SET status = 'booked', user_id = ? WHERE id = ?;
COMMIT;
```

`SELECT FOR UPDATE` 锁住行，其他事务等待。

### 乐观锁

表加 `version`：

```sql
UPDATE seats
SET status = 'booked', version = version + 1
WHERE id = ? AND version = ? AND status = 'available';
```

检查受影响行数是否为 1。若为 0，说明被抢。

### 唯一约束

对“座位 + 场次”加唯一约束，让数据库兜底。

应用层 mutex 只在单进程有效，多服务器无效。

## 6. 可重复读和可序列化隔离级别有什么区别？

以 PostgreSQL 为例：

- **Read Committed**：默认。每条语句看到最新已提交数据。可能不可重复读、幻读。
- **Repeatable Read**：事务内多次读同一行结果一致。Postgres 实现为快照隔离，可能写偏斜。
- **Serializable**：最强。让并发事务结果等价于某个串行顺序。Postgres 用 SSI 实现，可能因冲突回滚，需要重试。

什么时候用 Serializable？

- 金融转账、库存扣减、复杂约束检查。
- 不能容忍写偏斜的场景。

代价：

- 更多冲突、回滚、重试。
- 吞吐下降。

面试要点：Postgres 默认 Read Committed，不是 Repeatable Read；Serializable 不是靠锁全表，而是冲突检测/回滚。

## 7. 如何实现无单点故障的分布式锁？

单 Redis 实例做锁的问题是：实例宕机或主从切换时，锁可能丢失。

方案：

### Redlock

- 向多个独立 Redis 节点申请锁。
- 多数节点成功且总耗时小于锁 TTL，才算获得锁。
- 争议：Martin Kleppmann 认为它依赖时钟，仍不够安全；Redis 作者认为足够。

### ZooKeeper / etcd

更常见的强一致方案：

- ZooKeeper 临时顺序节点。
- etcd lease + revision。
- 基于 Raft 共识，具备线性一致性。
- 客户端会话失效时锁自动释放。

### 数据库锁

- 唯一约束、行锁、 advisory lock。
- 适合已有强一致数据库时。

关键：

- 锁要有 TTL 或会话绑定，避免死锁。
- 要能处理锁丢失后的 fencing token，防止旧持有者继续写。

## 8. 如何为支付重试端点实现幂等性？

核心：客户端每次重试带同一个 **幂等键**。

流程：

1. 客户端生成 `Idempotency-Key`，同一笔支付重试时复用。
2. 服务端收到请求，先查幂等表：

```sql
CREATE TABLE idempotency_keys (
  key TEXT PRIMARY KEY,
  request_hash TEXT,
  status TEXT,
  response_body JSONB,
  created_at TIMESTAMP
);
```

3. 如果 key 不存在：插入并处理支付。
4. 如果 key 已存在且成功：直接返回之前响应。
5. 如果 key 已存在但处理中：返回 409 或让客户端稍后重试。
6. 如果 key 已存在但请求体不同：拒绝，防止冲突。

注意：

- 幂等键要落库，且与业务操作在同一事务或可靠状态机中。
- 支付网关调用也要带幂等键。
- 设置合理过期时间，但支付类通常保留较久。
- 要处理“支付成功但响应失败”的情况：先记录状态，再返回。

## 9. 什么是缓存击穿/缓存蜂拥，如何预防？

缓存蜂拥：某个热点 key 过期瞬间，大量请求同时未命中，全部打到数据库。

预防：

- **互斥锁重建**：只允许一个线程/进程回源，其他等待。
- **逻辑过期**：value 里带逻辑过期时间，过期后异步刷新，旧值继续服务。
- **概率提前过期**：给 TTL 加随机抖动，避免同时失效。
- **永不过期 + 后台刷新**：适合热点数据。
- **本地缓存 + 分布式缓存**：减少 Redis 压力。

注意和缓存穿透、缓存雪崩区分：

- 穿透：查不存在的数据。
- 雪崩：大量 key 同时过期。
- 蜂拥：单个热点 key 失效。

## 10. 缓存用户资料，更新邮箱时如何失效？

两种常见模式：

### Cache-Aside

读：先查缓存，未命中查库，写回缓存。  
写：更新数据库，然后删除缓存。

为什么删除而不是更新？

- 避免并发写导致旧值覆盖新值。
- 删除更简单，下次读时重建。

### Write-Through

写：同时写数据库和缓存。  
优点：缓存较新。  
缺点：写延迟高，冷数据也占缓存。

权衡：

- 短 TTL：简单，但可能读到旧数据。
- 显式删除：更实时，但要处理删除失败。
- 延迟双删：更新库后删缓存，稍后再删一次，应对并发读旧值回填。
- 订阅 binlog 失效：如 Canal、Debezium，更可靠。

## 11. 为什么把 Redis 放在数据库前面会拖慢系统？

因为每次请求多一次网络往返。如果缓存命中率低：

- 请求先到 Redis，未命中。
- 再查数据库。
- 总延迟 = Redis 网络 + 数据库查询。
- Redis 没帮忙，反而增加开销。

需要监控：

- 命中率 = 命中次数 / 总请求。
- 如果命中率很低，缓存可能不值得。
- 计算收益：`节省的 DB 时间 * 命中率 > 缓存访问成本`。

优化：

- 只缓存热点数据。
- 本地缓存挡一层。
- 批量查询减少往返。
- 设置合理 TTL 和容量。

## 12. 会话商店和内容订阅源，驱逐政策哪个更合理？

- **内容订阅 feed**：LRU 合理。最近访问的内容更可能再次被访问。
- **会话商店**：LRU 可能有问题。活跃用户可能因为长时间不操作被驱逐，导致随机登出。

会话商店更适合：

- TTL 驱逐：按会话过期时间。
- 显式登出删除。
- 如果内存有限，可结合 LRU，但要保证活跃会话优先。
- 对“记住我”和短期会话分层存储。

核心：驱逐策略要匹配访问模式和数据价值。

## 13. 如何在不破坏现有移动客户端的情况下安全更改实时 API 负载？

原则：**向后兼容**。

做法：

- 只加字段，不删字段，不改字段类型。
- 新字段可选，旧客户端忽略。
- 用 API 版本：URL `/v2/` 或 Header `Accept: application/vnd.myapp.v2+json`。
- 弃用流程：先公告，再双写/双读，再监控旧版本流量，最后下线。
- 对移动端，保留旧版本可能数年。
- 用 Feature Flag 控制新行为。
- 契约测试和消费者驱动契约。

破坏性变更：

- 删除字段、改类型、改语义、改状态码。
- 必须发新版本，不能直接改旧版本。

## 14. 滑动窗口日志和固定窗口计数器在速率限制方面有什么区别？

### 固定窗口

- 每分钟一个计数器。
- 简单、内存少。
- 问题：边界突发。比如限制 100/分钟，用户在 12:00:59 发 100，12:01:00 再发 100，两秒内 200。

### 滑动窗口日志

- 记录每个请求时间戳。
- 查询过去 60 秒内的请求数。
- 精确，但内存大。
- 适合低 QPS 或精确计费。

### 滑动窗口计数器

- 当前窗口 + 上一窗口加权。
- 折中方案，内存小，平滑边界。
- 不是完全精确，但工程上常用。

面试要点：固定窗口简单但有边界问题；滑动日志精确但昂贵；滑动计数器是常用折中。

## 15. 如何设计上传 5GB 视频文件的端点？

不要让应用服务器把 5GB 读进内存。

方案：

### 预签名 URL

1. 客户端请求后端：我要上传视频。
2. 后端生成 S3/GCS 预签名 URL。
3. 客户端直接分块上传到对象存储。
4. 上传完成后，客户端通知后端。
5. 后端触发转码、审核等异步任务。

优点：

- 不经过应用服务器。
- 可断点续传。
- 可多部分上传。

### 流式上传

如果必须经过服务器：

- 使用流式解析，不缓冲整个文件。
- 限制大小、类型。
- 边收边写对象存储。

还要考虑：

- 分块校验、MD5。
- 上传完成后的合并。
- 病毒扫描、转码队列。
- 权限和过期时间。

## 16. 如何处理同步 API 请求中的长时间任务？

用异步工作模式。

流程：

1. 客户端 POST `/reports`。
2. API 立即返回 `202 Accepted` 和 `job_id`。
3. 后端把任务放入队列。
4. Worker 处理 PDF 生成。
5. 客户端轮询 `GET /jobs/{id}` 或通过 WebSocket/SSE 接收通知。
6. 完成后返回结果 URL 或状态。

好处：

- 避免 HTTP 超时。
- 可重试、可监控、可扩展。
- 客户端体验更好。

注意：

- 任务状态要持久化。
- 要设置超时、重试、死信队列。
- 结果存储用对象存储，不要放内存。

## 17. 为什么选 RabbitMQ 而不是 Kafka，或者反之？

### Kafka

- 分布式日志。
- 高吞吐、持久化、可重放。
- 消费者按 offset 读。
- 适合事件流、日志、数据管道、流处理。
- 顺序按分区保证。

### RabbitMQ

- 传统消息代理。
- 复杂路由：exchange、routing key、binding。
- 适合任务队列、RPC、延迟消息、优先级。
- 消息消费后通常删除。
- 吞吐低于 Kafka，但路由灵活。

选择：

- 需要重放、事件溯源、高吞吐：Kafka。
- 需要复杂路由、任务分发、低延迟：RabbitMQ。
- 云原生场景也可考虑 SQS、Pub/Sub、Pulsar。

## 18. Kafka 消费者读了消息但没提交 offset，会怎样？

消费者重启后会从上次提交的 offset 重新读，于是同一条消息会被再次处理。

后果：

- 至少一次语义。
- 可能重复处理。

解决：

- 处理逻辑必须幂等。
- 用唯一键、去重表、upsert。
- 事务性写出：读-处理-写 offset 在同一事务。
- Kafka 事务可实现精确一次，但有复杂度和限制。

面试要点：Kafka 默认不是精确一次；未提交 offset 导致重复消费，必须幂等。

## 19. 如何处理反复让 worker 崩溃的毒消息？

毒消息：一条消息反复导致消费者崩溃，无法前进。

解决：

- **重试次数限制**：记录 delivery count。
- **死信队列 DLQ**：超过重试次数后转入 DLQ。
- **告警和人工处理**。
- **隔离**：不要让毒消息阻塞整个分区。
- **验证和 schema 校验**：入口处拦截坏消息。
- **幂等和防御性编程**：空值、格式错误处理。

流程：

1. 消费失败。
2. 重试 N 次。
3. 仍失败则发到 DLQ。
4. 提交 offset，继续处理后续消息。
5. 运维检查 DLQ。

## 20. 如何确保消息按发送顺序处理？

在分布式队列中，全局顺序几乎不可能，也不值得追求。

保证相关消息有序：

- **分区键 / routing key**：同一订单、同一用户的消息进同一分区。
- **单消费者 per 分区**：Kafka 中一个分区同一时刻只被一个消费者线程消费。
- **单线程处理分区**：避免分区内并发。
- **数据库顺序约束**：版本号、序列号。
- **避免重试乱序**：重试可能打乱顺序，需要按 key 串行。

Kafka：

- 分区内有序。
- 全局有序需要单分区，吞吐受限。

RabbitMQ：

- 单队列单消费者可有序。
- 多消费者会乱序。

核心：顺序是按 key 的局部顺序，不是全局顺序。

## 总结性面试口诀

- 索引：随机 UUID 破坏 B+Tree 局部性，顺序/时间排序 UUID 更好。
- 分页：用游标，不用深 OFFSET。
- 复合索引：等值在前，范围/排序在后。
- N+1：JOIN 或批量急加载。
- 并发：锁、乐观版本、唯一约束。
- 隔离：Read Committed 默认，Serializable 最强但要重试。
- 分布式锁：Redlock 或 ZooKeeper/etcd，注意 fencing。
- 幂等：幂等键 + 唯一约束 + 状态机。
- 缓存：防击穿、防雪崩、防穿透，监控命中率。
- API：只加不删，版本化，弃用流程。
- 限流：固定窗口简单，滑动窗口平滑。
- 大文件：预签名 URL + 分块直传。
- 长任务：202 + job_id + 轮询/通知。
- 消息：Kafka 重放，RabbitMQ 路由；至少一次 + 幂等。
- 顺序：按 key 分区，单消费者，局部有序。
